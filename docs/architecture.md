# 구현 판단 기준

## 상태 관리

- 컴포넌트 내부 상태는 `useState`를 우선한다.
- 가까운 컴포넌트끼리만 쓰는 상태를 전역으로 올리지 않는다.
- 여러 컴포넌트·페이지가 공유하는 **클라이언트 상태**에만 Zustand를 고려한다.
- 서버 응답 데이터를 단순히 보관하려고 Zustand에 넣지 않는다.
- Zustand는 **클라이언트 전역 상태 전용**이다. 서버 데이터는 아래 기준을 따른다.

## 서버 상태

- 서버 데이터 조회·캐싱은 TanStack Query를 사용한다.
- 서버 응답을 Zustand나 `useState`에 복사해 보관하지 않는다.
- `queryKey`는 도메인과 식별자를 함께 담는다. 예: `['work', workId]`
- 공용 기본 옵션은 `shared/apis/queryClient.ts`에 두고, 개별 쿼리에서 필요할 때만 덮어쓴다.

## API

- HTTP 통신은 Axios를 사용하고, 공용 instance(`shared/apis/api.ts`의 `api`)를 반드시 쓴다.
- 요청 로직을 페이지나 UI 컴포넌트에 직접 쓰지 않고 API 모듈로 분리한다.
- 요청·응답 타입을 명시한다.
- API 명세가 있으면 명세를 우선하고, 없으면 응답 구조를 추측해서 확정 스키마처럼 쓰지 않는다.

## 스타일링

- Tailwind CSS를 사용하고, 특별한 이유가 없으면 inline style을 쓰지 않는다.
- 디자인 시안이 있으면 시안을 우선하며, 시안에 없는 스타일을 추가하거나 값을 바꾸지 않는다.
- 반응형을 고려하고, 모바일에서 의도치 않은 가로 스크롤이 생기지 않는지 확인한다.
- 반복되는 UI는 컴포넌트화를 고려하되, 파일 길이를 줄이려고 과하게 쪼개지 않는다.

## 추상화 기준

- 한 번만 쓰는 값은 상수로 빼지 않는다.
- 한 번만 쓰는 로직은 Custom Hook으로 분리하지 않는다.
